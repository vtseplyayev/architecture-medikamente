## Ключевые проектные решения

**1. Приватность обеспечивается блоками, а не регламентами.** Каждый принцип Privacy by Design закреплён за конкретным компонентом: приватность по умолчанию — режимом fail-closed в каталоге данных, встроенность — невозможностью получить доступ в обход точки принятия решения, подотчётность — append-only аудит-логом.

**2. Единая точка принятия решения о доступе.** Policy Decision Point проверяет роль, атрибуты и цель обработки на каждом запросе, а политики хранятся в Git как код. Правило «пациент видит только свои данные» существует в одном месте, а не в каждом сервисе — поэтому новые интеграции не требуют перевалидации.

**3. Персональные данные не покидают клинику.** Наружу — в лабораторию, партнёрам, в аналитику — уходит псевдоним `patient_ref`. Таблица соответствия живёт в изолированном домене с узким доступом.

**4. Обезличивание — обязательный шлюз на входе в аналитику, а не фильтр на выходе.** В аналитическом контуре персональных данных физически нет, поэтому BI, ML и LLM не расширяют область утечки, а модели не становятся носителями ПДн.

**5. Уведомления архитектурно не могут раскрыть врачебную тайну.** Сервис уведомлений не имеет доступа к домену медданных: пациенту уходит приглашение войти в личный кабинет, а не диагноз в SMS.

**6. Право на удаление исполнимо технически.** Ретенция берётся из тега, удаление каскадируется по `patient_ref`, а криптографическое стирание ключа субъекта покрывает резервные копии, из которых удалить одну запись невозможно.

**7. Филиалы не размножают архитектуру.** Филиал — атрибут в модели доступа, а не отдельная инсталляция с собственным файловым сервером.
