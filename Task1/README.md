Анализ текущего состояния (As-Is) работы компании с конфиденциальными данными, аудит мер защиты по требованиям законодательства РФ и доработанные потоки данных с механизмами защиты (To-Be).

## Ключевые выводы

**1. Компания обрабатывает специальную категорию персональных данных, не имея ни одной обязательной меры защиты.** Средняя зрелость — 1,2 из 5; из 18 проверенных требований 152-ФЗ, ПП № 1119 и приказа ФСТЭК № 21 не выполнены 17.

**2. Главный архитектурный дефект — единственная граница доверия.** Внутри периметра офиса действует модель полного доверия: кассир имеет технический доступ к диагнозам, ресепшен — к медкартам, администратор сети — ко всему без контроля. Это нарушает ст. 13 323-ФЗ о врачебной тайне внутри самой организации и перестаёт работать при переходе от 35 сотрудников к сотням в филиалах.

**3. Найдено 15 массивов конфиденциальных данных вне учёта систем** — сканы, вложения в почте, календари Outlook, бумажные журналы и согласия, выгрузки на рабочей станции аналитика. Пока нет перечня обрабатываемых ПДн, невозможно ни построить модель угроз, ни определить уровень защищённости, ни защитить данные.

**4. Самый опасный поток — обмен с лабораторией:** спецкатегория ПДн регулярно пересекает границу доверия по открытому e-mail, без шифрования, подписи и контроля целостности.

**5. Отсутствие журналирования порождает три невозможности:** расследовать инцидент, уведомить Роскомнадзор в течение 24 часов (ст. 21 ч. 3.1 152-ФЗ) и доказать соответствие требованиям при проверке.

**6. Compliance-риск монетизирован и растёт вместе с бизнесом.** С 30.05.2025 штраф за утечку — 3–15 млн ₽ в зависимости от числа субъектов, за повторную — оборотный (1–3 % выручки). После открытия филиалов база выйдет за 100 000 субъектов, что переводит компанию в верхний диапазон.

**7. Все три цели бизнеса заблокированы текущей архитектурой.** API лаборатории, озеро данных для BI/ML и портал с личным кабинетом нельзя построить поверх файлового обмена без классификации, разграничения доступа и аудита — иначе новая функциональность масштабирует существующую уязвимость.

## Предлагаемые решения

| Направление | Решение |
|-------------|---------|
| Хранение | PostgreSQL с пополевым шифрованием + объектное хранилище для документов, ключи в Vault, разделение доменов данных с отдельными ключами |
| Доступ | Keycloak (SSO, MFA) + OPA: RBAC как база, ABAC для медданных — «врач видит карту только при активной записи», «пациент видит только свои данные» |
| Классификация | Теги как машиночитаемый контракт: каталог данных → политики → шифрование, маскирование, ретенция, аудит; режим fail-closed для нетегированных данных |
| Интеграции | mTLS + OAuth 2.0, псевдонимизация в контрактах (ФИО не покидает клинику), УКЭП на медицинских документах |
| Аналитика | Обязательный слой обезличивания на входе в озеро данных по приказу РКН № 178, контроль k-анонимности |
| Наблюдаемость | Append-only аудит-лог в Elastic, детекторы аномального доступа, алертинг в Victoria Metrics, процедура уведомления РКН |
| Права субъекта | Дифференцированное исполнение по целям обработки + криптографическое стирание для покрытия резервных копий |

Инструменты подобраны в рамках стека, которым уже владеет команда: Java, PostgreSQL, ClickHouse, Elastic, Kubernetes, Victoria Metrics.
